# JobTrack — Project Plan

**Version:** 1.0  
**Status:** Approved planning baseline  
**Interface and documentation language:** English  
**Learning capacity:** 2–3 hours per study day  
**Project type:** Portfolio-oriented full-stack learning application

## 1. Vision and learning goals

JobTrack helps individuals privately organize and monitor job applications. The project is also a guided learning environment to strengthen mid-level React frontend skills, especially Jest and React Testing Library (RTL), and build practical full-stack experience.

### Success outcomes
- Build, explain, and maintain a complete React + Express + PostgreSQL application.
- Write behavior-focused frontend tests independently with Jest and RTL.
- Design and test REST endpoints, persistence, authentication, and authorization.
- Explain architectural tradeoffs and testing choices in interviews.
- Publish a documented, demonstrable portfolio project after security and deployment review.

## 3. Product scope

### 3.1 Personas and access
- A registered user can manage only their own applications.
- An unauthenticated visitor can register or log in but cannot access private application data.
- The MVP has one role (`user`); no administrators, teams, or sharing.

### 3.2 Authentication — MVP
- Register with email and password.
- Log in with valid credentials.
- Log out and invalidate the active authentication session according to the chosen token lifecycle.
- Persist authenticated state across a page reload while the session remains valid.
- Protect private frontend routes for user experience, and enforce authentication on the API.
- Provide safe, non-revealing authentication errors and validation feedback.
- No email verification, password reset, OAuth, or multi-factor authentication in the MVP.

### 3.3 Applications — MVP
- Create a job application.
- List only the signed-in user's applications.
- View details of one application.
- Edit an application.
- Delete an application after explicit confirmation.
- Search applications by company or position.
- Filter by status; optionally sort by recent activity.
- Show loading, empty, success, and failure states.

**Application fields**

| Field | Type | Requirement |
| --- | --- | --- |
| `id` | UUID | Generated by server |
| `userId` | UUID | Derived from authenticated user, never trusted from client |
| `company` | string | Required, trimmed, length-limited |
| `position` | string | Required, trimmed, length-limited |
| `status` | enum | Required; default `wishlist` |
| `jobUrl` | URL/string | Optional; validate acceptable HTTP(S) URL |
| `appliedAt` | date | Optional; may be absent for wishlist |
| `notes` | string | Optional, length-limited; rendered safely |
| `createdAt` | timestamp | Server-managed |
| `updatedAt` | timestamp | Server-managed |

**Statuses:** `wishlist`, `applied`, `interviewing`, `offer`, `rejected`. For the MVP, users may change between any statuses; historical transitions are not tracked. The `appliedAt` field remains optional and does not automatically change when status changes unless a future requirement explicitly introduces that behavior.

### 3.4 Dashboard — MVP
- Display the user's total application count.
- Display counts for each of the five statuses.
- Refresh counts after successful create, edit, and delete operations.
- Handle no applications and failed requests gracefully.

### 3.5 Kanban — MVP
- Display five columns, one for each status.
- Show each application in exactly one column.
- Allow changing an application's status using an accessible control or action.
- Reflect successful status updates in the board and other relevant views.
- Handle save failures without pretending the change succeeded.
- No drag-and-drop, custom columns, or stage history in the MVP.

### 3.6 Out of scope for MVP
Interview calendar and reminders, file attachments/CVs, email integrations, salary analytics, advanced reporting, drag-and-drop, multi-user teams, i18n, mobile native app, OAuth, and production-grade notification services.

## 4. User journeys

1. Visitor opens JobTrack, registers, logs in, and reaches the dashboard.
2. User creates a wishlist application with company and position.
3. User updates it to applied, optionally adding an application date and job URL.
4. User searches or filters the application list.
5. User moves the application to interviewing using the Kanban status action.
6. User sees updated dashboard counts.
7. User edits notes or deletes an application after confirmation.
8. User logs out and can no longer access protected API resources with that session.

## 5. Architecture

```text
Browser / React (apps/web)
  Pages → Components → Hooks → API client
  React Router; local state; TanStack Query when API integration begins
              │ HTTPS / JSON / cookies
              ▼
Express API (apps/api)
  Routes → validation/auth middleware → controllers → services → Prisma
              │
              ▼
PostgreSQL
```

### 5.1 Monorepo layout

```text
jobtrack/
├── apps/
│   ├── web/
│   │   ├── src/
│   │   └── package.json
│   └── api/
│       ├── src/
│       ├── prisma/
│       └── package.json
├── docs/
├── AGENTS.md
├── PROJECT_PLAN.md
├── README.md
├── .gitignore
└── package.json
```

Use npm workspaces. Avoid extra orchestration tools until a concrete need arises. Frontend starts with mock data; API and persistence are introduced progressively. Shared contracts can be considered later, but should not obscure HTTP boundaries or basic API design.

### 5.2 Backend boundaries
- **Routes:** Map HTTP methods and paths.
- **Middleware:** Authenticate requests, validate input, apply security controls, and handle errors.
- **Controllers:** Translate HTTP requests and service results into responses.
- **Services:** Own application logic and enforce per-user access.
- **Prisma layer:** Persist and query data; migrations version schema changes.
- **Centralized errors:** Return consistent status codes and safe error messages.

### 5.3 Data model

**User**: `id`, `email` (unique, normalized), `passwordHash`, `createdAt`, `updatedAt`.

**JobApplication**: fields in §3.3, with a foreign key to `User.id` and appropriate indexes (for example, `userId`, `status`, `createdAt`).

**Session/revocation records:** Add a server-side session or refresh-token record if required by the chosen JWT lifecycle to support effective logout and revocation. Finalize that mechanism before implementing auth.

Relationship: one User has many JobApplications; every JobApplication belongs to exactly one User. Never accept client-supplied `userId` as proof of ownership.

### 5.4 Initial REST API contract

| Method | Route | Purpose | Access |
| --- | --- | --- | --- |
| POST | `/api/auth/register` | Create account | Public |
| POST | `/api/auth/login` | Authenticate and set cookie | Public |
| POST | `/api/auth/logout` | End session / clear cookie | Authenticated |
| GET | `/api/auth/me` | Current user profile | Authenticated |
| GET | `/api/applications` | List/search/filter own applications | Authenticated |
| POST | `/api/applications` | Create application | Authenticated |
| GET | `/api/applications/:id` | View own application | Authenticated |
| PATCH | `/api/applications/:id` | Edit own application, including status | Authenticated |
| DELETE | `/api/applications/:id` | Delete own application | Authenticated |
| GET | `/api/dashboard/summary` | Own application counts | Authenticated |

**Proposed response rules:** `201` for creation, `200` for reads/updates, `204` for successful deletion/logout when no body is returned, `400` for invalid input, `401` for unauthenticated requests, `404` for missing or non-owned resources, `409` for duplicate registration where appropriate, and `500` for unexpected failures without leaking internal details. Agree on a consistent error body during API design. Paginate list endpoints if data size requires it; the MVP should avoid unbounded queries in production.

## 6. Security and authentication design

- Hash passwords using a vetted adaptive algorithm such as Argon2id; never store plaintext passwords.
- Sign JWTs with securely managed secrets/keys; validate signature, algorithm, issuer/audience as configured, and expiration.
- Store auth tokens only in `HttpOnly` cookies with `Secure` in HTTPS environments and an appropriate `SameSite` policy; do not store auth JWTs in localStorage.
- **HttpOnly does not prevent CSRF.** Use CSRF protection for state-changing cookie-authenticated requests, together with appropriate Origin/Referer checks and SameSite settings.
- Use restrictive CORS settings if frontend and API are on different origins; never combine wildcard origins with credentials.
- Rate-limit authentication endpoints and avoid user-enumerating error messages.
- Enforce user ownership in every application query and mutation.
- Use server-side validation and Prisma parameterization; avoid exposing stack traces, secrets, or password hashes.
- Keep secrets in environment variables, never commit `.env` values.
- Design token expiration, rotation/revocation, and logout before implementation. Clearing a cookie alone does not immediately revoke an otherwise valid JWT.
- Use HTTPS in deployment and review cookie domain/path settings.
- Add accessibility checks and safe rendering of user-generated notes/URLs.

## 7. Testing strategy

### 7.1 Frontend — Jest + RTL
- Test behavior users can observe, not internal React implementation details.
- Prefer accessible queries (`getByRole`, `getByLabelText`, `findByRole`).
- Use `user-event` for realistic interaction sequences.
- Cover validation, successful submission, failed submission, loading, empty states, filters, confirmation dialogs, protected routes, and status updates.
- Use MSW to intercept API calls at the network boundary.
- Test async flows with appropriate async queries and `waitFor` where needed.
- Do not mock every child component or assert private state unnecessarily.
- Configure Jest for Vite/TypeScript intentionally; Vite does not configure Jest automatically.

### 7.2 Backend — Jest + Supertest
- Unit-test service rules and validation helpers.
- Test API routes using Supertest against the Express application without requiring a separately running HTTP server.
- Cover auth failures, malformed payloads, duplicate email, not-found responses, success responses, and ownership enforcement.
- Use an isolated test PostgreSQL database for integration tests, with deterministic setup/cleanup.
- Test actual persistence and authorization at least for critical CRUD paths.

### 7.3 Test pyramid and quality gates
- Many fast unit/component tests; fewer integration tests; optional Playwright E2E tests after MVP.
- Each feature includes happy path, at least one failure path, and relevant edge cases.
- No fixed coverage target initially; track coverage trends and meaningful untested branches. Introduce thresholds after a baseline exists.
- CI eventually runs type checking, linting, and test suites. Database tests must use a disposable test database.
- Tests must be deterministic, isolated, and runnable with documented commands.

### 7.4 Example learning exercises
1. Render a status badge and assert accessible text.
2. Validate a required company field.
3. Test form submission using `user-event`.
4. Mock a successful and failed API response with MSW.
5. Test status filtering and empty results.
6. Test auth-required API routes and cross-user access denial.
7. Test dashboard count changes after a successful mutation.

## 8. Acceptance criteria

### Authentication
- [ ] Valid registration creates a user with a hashed password and no exposed hash.
- [ ] Duplicate/invalid registration receives an appropriate safe error.
- [ ] Correct credentials authenticate; incorrect credentials do not.
- [ ] Protected API routes return `401` without valid authentication.
- [ ] An active session survives reload until expiration or logout.
- [ ] Logout prevents reuse of the ended session according to the documented revocation design.
- [ ] Cookie-authenticated mutations are protected against CSRF.

### Applications
- [ ] Authenticated user can create with required company and position.
- [ ] Missing/invalid fields show clear validation feedback.
- [ ] User can list, view, edit, and delete own records.
- [ ] Delete requires confirmation in the UI.
- [ ] Search and status filter return expected own records.
- [ ] A second user cannot read, edit, or delete the first user's records.
- [ ] Loading, empty, and error states are distinguishable and accessible.

### Dashboard and Kanban
- [ ] Dashboard counts match the signed-in user's records.
- [ ] Each application appears in exactly one Kanban status column.
- [ ] Status can be changed without drag-and-drop.
- [ ] Failed status update displays an error and does not falsely show a saved state.
- [ ] Successful CRUD/status changes are reflected in relevant views.

### Engineering and portfolio
- [ ] Relevant frontend and backend tests pass.
- [ ] Type checks and lint checks pass.
- [ ] Setup and test commands are documented.
- [ ] No secrets or real personal application data are committed.
- [ ] README explains architecture, features, test approach, and key tradeoffs.
- [ ] Deployment is reviewed for authentication, CORS, CSRF, HTTPS, and environment configuration before public launch.

## 10. Guided ChatGPT + Codex workflow

### Responsibilities
**Learner:** Owns decisions, writes designated exercises/tests, reviews changes, runs code, and explains outcomes.

**ChatGPT:** Explains concepts, breaks work into tasks, sets acceptance criteria, designs exercises, reviews tradeoffs, and drafts focused Codex prompts.

**Codex:** Helps scaffold, inspect, refactor, and debug code within a tightly defined scope; reviews learner-written code; reports changes and test results.

### Feature cycle
1. Define a small user story and acceptance criteria.
2. Identify concepts to learn and what the learner will write unaided.
3. For suitable exercises, write a failing test first (TDD).
4. Implement the smallest working change.
5. Use Codex for targeted assistance or review, not automatic completion of reserved exercises.
6. Run relevant tests, type checks, and lint checks; inspect failures.
7. Refactor, document decisions, and make a descriptive commit.
8. Explain the implementation and one tradeoff in plain English.

### Rules for `AGENTS.md` (to create during M1)
- Use strict TypeScript; avoid unjustified `any`.
- Do not introduce dependencies without stating the purpose.
- Change only files relevant to the requested task.
- Preserve architecture and existing tests; do not remove tests to hide failures.
- Keep exercises explicitly marked as learner-owned untouched unless asked to review.
- Explain what changed, why, and how it was verified.
- Do not claim tests passed without running them.
- Flag security-sensitive changes for explicit review.
- Keep docs and acceptance criteria updated when decisions change.

### Task definition template
- **Story:** What the user can do.
- **Learning goal:** One or two skills to practice.
- **Scope:** Files/features allowed.
- **Learner-owned work:** Code/tests not delegated to Codex.
- **Acceptance criteria:** Observable behaviors.
- **Verification:** Commands and manual checks.
- **Review questions:** Why this implementation and how it could fail.

## 11. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Scope creep | Keep MVP bounded; maintain a separate backlog |
| Codex dependency | Reserve exercises for learner and require explanations |
| Jest + Vite friction | Configure Jest deliberately; start with one passing test |
| JWT cookie security mistakes | Design CSRF, expiry, revocation, and CORS before auth coding |
| Slow database setup | Use a local PostgreSQL instance or container; document reproducible setup |
| Fragile tests | Prefer accessible behavior, MSW, deterministic fixtures |
| Overengineering | Add abstractions and packages only when justified |
